## 1. 인증 (AUTH)

### SC-AUTH-001: 관리자가 신규 사용자를 초대한다 (정상 흐름)

| 항목 | 내용 |
|------|------|
| **기능 ID** | AUTH-001 |
| **역할** | ADMIN |

**Pre**: 관리자가 로그인 상태. 초대할 이메일·사번이 미등록 상태.

**Steps**:
1. 관리자 → 사용자 관리 → [초대] 버튼 클릭
2. 이름, 이메일, 사번(6~10자리), 역할(관리자/일반) 입력
3. [초대 발송] 클릭

**Result**:
- 관리자 화면에 "초대 메일이 발송되었습니다" 토스트 표시
- `users` 테이블에 `status='pending'` 레코드 생성
- 수신자 이메일 수신함에 24시간 유효 초대 링크 포함 메일 도착

---

### SC-AUTH-002: 초대받은 사용자가 비밀번호를 설정하고 계정을 활성화한다

| 기능 ID | AUTH-001 |
|---------|---------|

**Pre**: `SC-AUTH-001` 완료. 초대 링크 유효(24시간 이내).

**Steps**:
1. 이메일에서 초대 링크 클릭
2. 비밀번호 설정 폼에서 새 비밀번호 입력 (최소 10자, 영문+숫자+특수문자 각 1자 이상)
3. 비밀번호 확인 입력
4. [설정 완료] 클릭

**Result**:
- `users.status` → `'active'`
- 자동 로그인 후 대시보드로 이동

---

### SC-AUTH-003: 초대 링크 만료(24시간 초과) 후 접근 시 오류 처리

| 기능 ID | AUTH-001 |
|---------|---------|

**Pre**: 초대 발송 후 24시간 초과.

**Steps**:
1. 만료된 초대 링크 클릭

**Result**: "초대 링크가 만료되었습니다" 안내 + [관리자에게 재초대 요청] 버튼 표시

---

### SC-AUTH-004: 이메일 중복·사번 중복 초대 시도

| 기능 ID | AUTH-001 |
|---------|---------|

**Pre**: 이미 등록된 이메일 또는 사번 보유.

**Steps**:
1. 중복 이메일/사번으로 초대 폼 제출

**Result**:
- 이메일 중복 → "이미 등록된 이메일입니다" 안내
- 사번 중복 → "이미 사용 중인 사번입니다" 안내
- 초대 발송 안 됨

---

### SC-AUTH-005: 이메일+비밀번호로 로그인 (정상)

| 기능 ID | AUTH-002 |
|---------|---------|

**Pre**: `status='active'` 계정 보유. 브라우저 쿠키 활성화.

**Steps**:
1. 로그인 화면에서 "이메일로 로그인" 선택

### SC-AUTH-006: 사번+비밀번호로 로그인 (정상)

| 기능 ID | AUTH-002 |
|---------|---------|

**Pre**: `status='active'` 계정 보유.

**Steps**:
1. 로그인 화면에서 "사번으로 로그인" 선택
2. 사번(6~10자리 숫자), 비밀번호 입력 → [로그인] 클릭

### SC-AUTH-007: 5회 연속 로그인 실패 후 계정 잠금

| 기능 ID | AUTH-002 |
|---------|---------|

**Steps**:
1. 잘못된 비밀번호로 로그인 5회 연속 시도

- `status='locked'`

## 2. 권한 (PERM)

### SC-PERM-001: 일반 사용자가 관리자 전용 화면 직접 URL 접근 시도

| 기능 ID | PERM-001, PERM-004 |
|---------|---------|

**Pre**: `role='user'` 계정으로 로그인.

**Steps**:
1. 주소창에 `/admin/users` 직접 입력

**Result**: 대시보드로 이동. 관리자 메뉴는 사이드바에 표시되지 않음.

---

### SC-PERM-002: 역할 정보 로드 실패 시 최소 권한 적용

| 기능 ID | PERM-001 |
|---------|---------|

**Pre**: 서버 역할 조회 일시 오류.

**Result**: 일반 사용자(`user`) 권한으로 처리. 관리자 기능 차단.

---

### SC-PERM-003: 관리자가 대리 입력 권한을 부여한다

| 기능 ID | PERM-002 |
|---------|---------|

**Pre**: ADMIN 로그인. 대리 입력자(A)와 대상 임원(B) 모두 등록된 상태. A≠B.

**Steps**:
1. 관리자 → 권한 관리 → [대리 입력 권한 추가]
2. 대리 입력자(A) 선택, 대상 임원(B) 선택
3. [확인] 클릭

**Result**:
- `proxy_permissions` 에 `revoked_at=NULL` 레코드 생성
- "A에게 B의 대리 입력 권한을 부여했습니다" 토스트
- `audit_logs` 기록

---

### SC-PERM-004: 중복 대리 입력 권한 부여 시도

| 기능 ID | PERM-002 |
|---------|---------|

**Pre**: A→B 대리 권한 이미 존재.

**Steps**:
1. 동일한 A→B 권한을 다시 부여 시도

**Result**: "이미 부여된 권한입니다" 안내. 중복 생성 안 됨.

---

### SC-PERM-005: 관리자가 대리 입력 권한을 해제한다

| 기능 ID | PERM-002 |
|---------|---------|

**Pre**: A→B 활성 대리 권한 존재.

**Steps**:
1. 권한 목록에서 해당 항목 → [해제] 클릭

**Result**:
- `proxy_permissions.revoked_at` = 현재 시각으로 갱신
- 이후 A의 B 대리 입력 즉시 차단
- 재부여 시 신규 레코드 생성 (이력 분리)

---

### SC-PERM-006: 대리 입력자가 대리 입력 실행 중 권한 해제 시 재검증 차단

| 기능 ID | PERM-003 |
|---------|---------|

**Pre**: A가 B의 일정 등록 폼 작성 중. 관리자가 권한을 해제함.

**Steps**:
1. A가 [저장] 클릭

**Result**: 저장 시점 재검증 → "해당 임원에 대한 대리 입력 권한이 없습니다" 안내. 저장 안 됨.

---

### SC-PERM-007: 일반 사용자가 타인 일정 수정 버튼을 볼 수 없다

| 기능 ID | PERM-004 |
|---------|---------|

**Pre**: `role='user'` 로그인. 타인(C)의 개인 일정 조회.

**Result**: [수정][삭제] 버튼이 렌더링되지 않음 (읽기 전용).

---

### SC-PERM-008: 대리 입력 권한 보유자에게만 "대리 입력 대상" 드롭다운이 표시된다

| 기능 ID | PERM-004 |
|---------|---------|

**Pre**: A는 B에 대한 대리 권한 보유. C는 대리 권한 없음.

**Result**:
- A의 일정 등록 폼: "입력 대상" 드롭다운 표시 (B 선택 가능)
- C의 일정 등록 폼: "입력 대상" 드롭다운 없음

---

### SC-PERM-009: 관리자 계정 비활성화 후 세션 유지 중 다음 요청 시 차단

### SC-PERM-010: 본인에게 대리 권한 부여 시도

## 3. 일정 관리 (SCH)

### SC-SCH-001: 개인 일정 등록 (정상, 본인)

| 기능 ID | SCH-001 |
|---------|---------|

**Pre**: 로그인 상태.

**Steps**:
1. [일정 등록] 클릭 → 유형: "개인"
2. 일정 주인: 본인 자동 선택
3. 날짜: "내일" 또는 `2026-06-01` 형식 입력
4. 시작 시간 `09:00`, 종료 시간 `10:00` 입력 (시간대 자동: 오전)
5. 일정 내용 입력 (1~200자)
6. [저장]

**Result**:
- `schedules` 레코드 생성 (`type='personal'`, `owner_id`=본인)
- `audit_logs` 에 `action='created'` 기록 (트리거 자동)
- 달력 해당 날짜에 일정 카드 즉시 표시

---

### SC-SCH-002: 종일 일정 등록

| 기능 ID | SCH-001 |
|---------|---------|

**Steps**:
1. 일정 등록 폼 → 종일 토글 ON
2. 시간 입력 필드 비활성화 확인
3. 시간대 = "전일" 고정 확인
4. [저장]

**Result**: `time_slot='allday'`, `start_time=NULL`, `end_time=NULL` 저장.

---

### SC-SCH-003: 날짜 자연어 파싱 지원 검증

| 기능 ID | SCH-001 |
|---------|---------|

| 입력 | 예상 파싱 결과 |
|------|--------------|
| `내일` | 오늘 + 1일 |
| `모레` | 오늘 + 2일 |
| `다음주 월요일` | 다음 주 월요일 |
| `5/11` | 당해 연도 5월 11일 |
| `이번주 금요일` | 이번 주 금요일 |

**Error**: 파싱 불가 입력 → "날짜 형식을 확인해주세요" 인라인 오류. [저장] 버튼 비활성화.

---

### SC-SCH-004: 시작 시간 > 종료 시간 입력 시 오류

| 기능 ID | SCH-001 |
|---------|---------|

**Steps**:
1. 시작 시간 `14:00`, 종료 시간 `13:00` 입력
2. [저장] 클릭

**Result**: "종료 시간은 시작 시간 이후여야 합니다" 인라인 오류. 저장 차단.

---

### SC-SCH-005: 대리 입력자가 임원 명의로 일정 등록

| 기능 ID | SCH-001, SCH-006, PERM-003 |
|---------|---------|

**Pre**: A가 B에 대한 대리 입력 권한 보유.

**Steps**:
1. A가 일정 등록 폼 진입
2. "입력 대상" 드롭다운에서 B 선택
3. "B 이름으로 입력 중" 경고 배너 확인
4. 일정 내용 작성 → [저장]

**Result**:
- `schedules.owner_id` = B (명의 임원)
- `schedules.created_by` = A (실제 작성자)
- `audit_logs.actor_id` = A, `audit_logs.on_behalf_of_id` = B
- 일정 상세에 "B의 일정 / 실제 작성자: A (대리 입력)" 표시

---

### SC-SCH-006: 일정 수정 (본인 일정)

## 절대 하지 말아야 할 것 (설계 원칙 위반 시나리오)

> 아래 항목은 시스템이 **반드시 차단해야 하는** 동작이다. 테스트 시 이 동작이 발생하면 버그로 처리한다.

| 위반 항목 | 올바른 처리 |
|----------|-----------|
| `audit_logs` 직접 INSERT | 트리거 자동 처리 |
| `deleted_at IS NOT NULL` 행 일반 조회에 포함 | 모든 쿼리 `deleted_at IS NULL` 조건 필수 |
| 물리 삭제 (`DELETE FROM schedules`) | soft delete만 허용 |
| Service Role 키를 클라이언트 컴포넌트에서 사용 | 서버 전용 |
| 공휴일·주말 일정 등록 차단 | 차단 없음 |
| 역할 3종 이상 (`admin`/`user` 외 추가) | 2종만 |
| `revoked` 대리 권한을 `active`로 직접 전환 | 신규 레코드 생성 |
