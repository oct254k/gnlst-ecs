# 11. 알림 (Notification)

**관련 프로세스**: [process/proc_05_notification.md](../process/proc_05_notification.md)

일정 등록·수정 이벤트 발생 시 관련 임원에게 이메일로 알린다.

---

## 알림 트리거 매트릭스

| 이벤트 | 발송 대상 | 채널 |
|--------|-----------|------|
| 공통 일정 등록 | 전체 임원 | 이메일 |
| 공통 일정 수정 | 전체 임원 | 이메일 |
| 내 일정을 타인이 수정 | 해당 임원 1명 | 이메일 |
| 신규 임원 초대 | 초대받은 임원 | 이메일 |
| 비밀번호 찾기 | 요청한 사용자 | 이메일 |

---

## 알림 상태 정의

### 상태 목록

| 상태값 | 의미 | 종료 상태 여부 |
|--------|------|:----------:|
| `pending` | 발송 요청이 접수되어 처리 대기 중 | ❌ |
| `retrying` | 발송 실패 후 재시도 중 | ❌ |
| `sent` | 발송 성공 | ✅ |
| `failed` | 재시도 횟수를 모두 소진한 최종 실패 | ✅ |
| `skipped` | 수신자 이메일 주소 없음 등의 이유로 발송 생략 | ✅ |

### 상태 전이 규칙

| From | To | 조건 |
|------|----|------|
| (없음) | `pending` | 알림 트리거 이벤트 발생 (일정 등록·수정 등) |
| `pending` | `sent` | 이메일 발송 성공 |
| `pending` | `retrying` | 발송 실패, 재시도 가능 횟수 남음 (최대 3회) |
| `pending` | `skipped` | 수신자 이메일 주소 없거나 발송 조건 미충족 |
| `retrying` | `sent` | 재시도 발송 성공 |
| `retrying` | `retrying` | 재시도 발송 실패, 재시도 가능 횟수 남음 |
| `retrying` | `failed` | 재시도 3회 모두 실패 |

### 재시도 정책

| 항목 | 정책 |
|------|------|
| 최대 재시도 횟수 | 3회 |
| 재시도 간격 | 지수 백오프 (1분 → 5분 → 15분) |
| 최종 실패 처리 | `failed` 상태로 기록. 관리자가 알림 이력에서 확인 가능 |

### 알림 이력 보존 항목

| 항목 | 설명 |
|------|------|
| 트리거 이벤트 | 알림을 발생시킨 이벤트 유형 |
| 수신자 | 알림을 받을 대상 임원 |
| 상태 | 현재 발송 상태 |
| 시도 횟수 | 발송 시도 횟수 (초기 1회 + 재시도 최대 3회) |
| 최종 처리 일시 | 최종 상태로 전이된 일시 |

## NOT-001: 공통 일정 등록 알림

| 항목 | 내용 |
|------|------|
| **기능 ID** | NOT-001 |
| **기능명** | 공통 일정 등록 알림 (전체 임원 → 이메일) |
| **버전** | 1.0 |

### 설명

공통 일정이 등록되면, 활성 상태인 **전체 임원**에게 일정 내용을 담은 알림 메일을 발송한다.

### 사전 조건

- 일정 등록 완료
- 알림 수신 대상 임원의 이메일 주소 존재

### 입력값

| 필드 | 타입 | 설명 |
|------|------|------|
| 일정 ID | 식별자 | 등록된 일정 ID |
| 이벤트 유형 | 코드 | 등록(`created`) |

### 처리 흐름

1. 공통 일정 등록이 완료된다
2. 시스템이 알림 발송 절차를 시작한다
3. 등록된 일정의 상세 정보를 조회한다 (제목, 일시, 장소, 등록자)
4. 활성 임원 전체의 이메일 목록을 조회한다
5. 시스템이 알림 대상자 전원에게 일정 등록 알림 메일을 발송한다
6. 발송 결과를 알림 이력에 기록한다

### 메일 템플릿 내용

```
제목: [일정 알림] {일정 제목} - {날짜}

본문:
  안녕하세요, {임원 이름}님.
  
  새로운 공통 일정이 등록되었습니다.

  ■ 일정명: {title}
  ■ 일시:   {start_at} ~ {end_at}
  ■ 장소:   {location | "미정"}
  ■ 등록자: {creator_name}
  
  자세한 내용은 일정 시스템에서 확인하세요.
```

### 출력

- 전체 임원 이메일 발송
- 알림 이력 저장 (수신자, 성공/실패, 발송 시각)

### 예외 처리

| 예외 상황 | 처리 방법 |
|-----------|-----------|
| 알림 발송 절차 호출 실패 | 1회 재시도 후 무시 (알림 실패가 일정 등록을 취소하지 않음) |
| 특정 임원 메일 발송 실패 | 해당 건만 이력에 실패 기록, 나머지 발송 계속 |
| 이메일 주소 없는 임원 | 해당 임원 건너뜀, 경고 기록 |
| 발송 서비스 처리량 초과 | 지수 백오프 방식으로 최대 3회 재시도 |

## NOT-002: 공통 일정 수정 알림

| 항목 | 내용 |
|------|------|
| **기능 ID** | NOT-002 |
| **기능명** | 공통 일정 수정 알림 (전체 임원 → 이메일) |
| **버전** | 1.0 |

### 설명

공통 일정이 수정되면 전체 임원에게 변경 내용을 담은 알림 메일을 발송한다.

### 사전 조건

- 공통 일정 수정 완료
- 수정 이전/이후 값이 이력에 저장된 상태

### 입력값

| 필드 | 타입 | 설명 |
|------|------|------|
| 일정 ID | 식별자 | 수정된 일정 ID |
| 이벤트 유형 | 코드 | 수정(`updated`) |
| 변경된 항목 목록 | 문자열 배열 | 메일 본문 표시용 |

### 처리 흐름

1. 공통 일정 수정이 완료된다
2. 시스템이 알림 발송 절차를 시작한다
3. 수정된 일정 상세 및 변경 전후 값을 조회한다
4. 전체 임원 이메일 목록을 조회한다
5. 시스템이 알림 대상자 전원에게 일정 변경 알림 메일을 발송한다
6. 발송 결과를 알림 이력에 기록한다

### 메일 템플릿 내용

```
제목: [일정 변경] {일정 제목} - {날짜}

본문:
  안녕하세요, {임원 이름}님.
  
  공통 일정이 수정되었습니다.

  ■ 일정명: {title}
  ■ 변경된 항목:
    - 일시: {old_start_at} → {new_start_at}
    - 장소: {old_location} → {new_location}
    (변경되지 않은 항목은 표시 생략)

  ■ 수정자: {modifier_name}
```

### 예외 처리

NOT-001과 동일한 예외 처리 정책 적용.

## NOT-003: 타인 일정 수정 알림

| 항목 | 내용 |
|------|------|
| **기능 ID** | NOT-003 |
| **기능명** | 타인 일정 수정 알림 (해당 임원 → 이메일) |
| **버전** | 1.0 |

### 설명

개인 일정을 **일정 소유자가 아닌 타인(관리자/비서)**이 수정할 경우, 일정 소유 임원에게 단독으로 알림 메일을 발송한다.

### 사전 조건

- 수정자와 일정 소유자가 다름
- 일정 수정 완료

### 입력값

| 필드 | 타입 | 설명 |
|------|------|------|
| 일정 ID | 식별자 | 수정된 일정 ID |
| 이벤트 유형 | 코드 | 타인에 의한 수정(`updated_by_other`) |
| 알림 수신 임원 ID | 식별자 | 일정 소유자 |
| 수정자 ID | 식별자 | 실제 수정한 사용자 |

### 처리 흐름

1. 수정자와 일정 소유자가 다름을 감지한다
2. 시스템이 알림 발송 절차를 시작한다
3. 일정 소유 임원의 이메일을 조회한다 (단일 대상)
4. 수정자 이름을 조회한다
5. 시스템이 일정 소유 임원에게 알림 메일을 발송한다
6. 발송 결과를 알림 이력에 기록한다

### 메일 템플릿 내용

```
제목: [내 일정 변경 알림] {일정 제목}

본문:
  안녕하세요, {임원 이름}님.

  귀하의 일정이 다른 사용자에 의해 수정되었습니다.

  ■ 일정명: {title}
  ■ 수정자: {modifier_name}
  ■ 수정 일시: {modified_at}
  ■ 변경 항목: (변경 전 → 후 표시)

  이상이 있으시면 담당자에게 문의하세요.
```

### 예외 처리

| 예외 상황 | 처리 방법 |
|-----------|-----------|
| 소유자와 수정자가 동일 | 알림 발송 절차 자체를 실행하지 않음 |
| 수신 임원 이메일 없음 | 이력 기록 후 건너뜀 |

## NOT-004: 초대 메일

| 항목 | 내용 |
|------|------|
| **기능 ID** | NOT-004 |
| **기능명** | 초대 메일 |
| **버전** | 1.0 |

### 설명

관리자가 새 임원 계정을 생성할 때 시스템이 초대 메일을 자동 발송한다.

### 사전 조건

- 호출자가 관리자 권한 보유 (서버에서 처리)
- 대상 이메일이 기존 계정과 중복되지 않음

### 입력값

| 필드 | 타입 | 설명 |
|------|------|------|
| 이메일 | 문자열 | 초대할 임원 이메일 |
| 이름 | 문자열 | 임원 이름 (초대 완료 후 프로필 생성용) |

### 처리 흐름

1. 관리자가 임원 등록 폼을 제출한다
2. 시스템이 초대 메일을 자동 발송한다 (메일에 초대 링크 포함, 만료: 24시간)
3. 임원 레코드가 시스템에 생성된다
4. 초대 성공 응답을 반환한다

### 출력

- 초대 이메일 발송 (링크 유효시간: 24시간)
- 임원 레코드 생성

### 예외 처리

| 예외 상황 | 처리 방법 |
|-----------|-----------|
| 이미 가입된 이메일 | "이미 등록된 이메일입니다" 표시 |
| 초대 이메일 발송 실패 | 재발송 기능 UI 제공 |
| 초대 만료(24시간) | 관리자 화면에서 재초대 버튼 제공 |

## NOT-005: 비밀번호 찾기 메일

| 항목 | 내용 |
|------|------|
| **기능 ID** | NOT-005 |
| **기능명** | 비밀번호 찾기 메일 |
| **버전** | 1.0 |

### 설명

로그인 화면의 "비밀번호 찾기" 클릭 시 시스템이 비밀번호 재설정 링크 메일을 자동 발송한다.

### 사전 조건

- 입력한 이메일이 등록된 계정에 존재

### 처리 흐름

1. 사용자가 비밀번호 찾기 폼에서 이메일을 입력한다
2. 시스템이 비밀번호 재설정 메일을 자동 발송한다
3. 사용자에게 "이메일을 확인하세요" 안내 메시지를 표시한다 (이메일 존재 여부 노출 안 함 — 보안)

### 출력

- 비밀번호 재설정 이메일 (재설정 링크 만료: 60분)

### 예외 처리

| 예외 상황 | 처리 방법 |
|-----------|-----------|
| 미등록 이메일 | 보안상 동일한 "이메일을 확인하세요" 메시지 표시 (이메일 존재 여부 노출 방지) |
| 재설정 링크 만료 | 재설정 페이지에서 "링크가 만료되었습니다" 안내 + 재전송 버튼 |

## NOT-006: 알림 메일 발송 이력

| 항목 | 내용 |
|------|------|
| **기능 ID** | NOT-006 |
| **기능명** | 알림 메일 발송 이력 기록 |
| **버전** | 1.0 |

### 설명

NOT-001~NOT-003에서 알림 메일이 발송될 때마다 발송 결과를 이력으로 기록한다. 이 이력을 통해 발송 성공 여부 및 수신 대상을 추적할 수 있다.

### 알림 이력 데이터 모델

> ERD `notification_logs` (E09) 와 1:1 매핑. 본 표는 NOT-006 관점에서의 핵심 필드 요약이며, 정식 컬럼 정의는 `erd/erd.md §E09` 참조.

| 필드명 | 타입 | 설명 |
|--------|------|------|
| `id` | 식별자 | 이력 고유 ID |
| `event_type` | 코드 | `common_schedule_created` / `common_schedule_updated` / `schedule_updated_by_other` / `invite` / `password_reset` |
| `recipient_id` | 식별자 | 수신자 user_id (외부 이메일만 있는 경우 NULL) |
| `recipient_email` | 문자열 | 수신 이메일 (스냅샷, 행당 1건. 다수 발송은 다수 행으로 분리 저장) |
| `target_type` | 코드 | `schedule` / `user` / NULL |
| `target_id` | 식별자 | 관련 대상 ID (예: 연관 일정 schedule_id, NULLABLE) |
| `status` | 코드 | `pending` / `retrying` / `sent` / `failed` / `skipped` |
| `attempt_count` | 숫자 | 시도 횟수 (0~4) |
| `last_attempted_at` | 일시 | 마지막 시도 시각 |
| `sent_at` | 일시 | 최종 발송 성공 시각 |
| `read_at` | 일시 | 수신자가 알림을 읽은 시각. 미확인 카운트는 `read_at IS NULL AND status='sent'` |
| `error_message` | 문자열 | 마지막 실패 사유 |
| `payload` | 객체 | 메일 본문 데이터 스냅샷 |
| `created_at` | 일시 | 생성 시각 |
| `updated_at` | 일시 | 마지막 수정 시각 |

### 관리자 이력 화면 렌더링 규칙

관리자가 알림 이력 화면(`SCR-ADMIN-NOTIFICATION-LOG`)을 조회할 때 실패 건수를 한눈에 파악할 수 있도록 아래 규칙을 적용한다.

| 요소 | 규칙 |
|------|------|
| 상단 실패 요약 배지 | 화면 상단에 `❗실패 n건` 배지 표시 (`status='failed'` 행 수 기준). 0건이면 숨김. |
| `failed` 행 강조 | `status='failed'`인 행의 배경색을 `#FFF5F5`(연빨강)으로 적용 |
| `skipped` 행 | 기본 배경 유지, 별도 강조 없음 |
| 기본 필터 | `status=all` (전체 표시). 사용자가 `status=failed`로 필터링 가능 |

> `❗실패 n건` 배지 데이터는 `GET /admin/notification-logs` 응답의 `data.summary.failed_count` 필드를 사용.

### 예외 처리

| 예외 상황 | 처리 방법 |
|-----------|-----------|
| 메일 발송 실패 | 이력에 실패 기록 후 처리 계속 (발송 실패가 일정 작업 실패를 의미하지 않음) |
| 수신자 목록 0명 | 발송 생략, 이력에 '생략' 기록 |
| 수신자 수가 많아 처리 지연 시 | 일괄 발송 방식으로 처리 |
