## 권한 모델 개요

### 역할 정의

| 역할 | 코드 | 설명 |
|------|------|------|
| 관리자 | `admin` | 시스템 전반 관리. 사용자 초대, 권한 부여, 전체 일정 수정 가능 |
| 일반 | `user` | 전체 일정 조회, 본인 일정 등록/수정 가능 |
| 대리 입력 | (권한 플래그) | `user` 역할에 추가되는 권한. 지정된 임원의 일정을 대신 등록 가능 |

> 대리 입력 권한은 역할과 독립적으로 별도 관리되며, 관리자가 사용자별로 특정 임원에 대한 대리 입력 권한을 부여한다.

### 관리자 vs 일반 사용자 권한 비교표

| 기능 | 관리자 | 일반 | 비고 |
|------|:------:|:----:|------|
| 전체 일정 조회 | ✅ | ✅ | |
| 본인 일정 등록 | ✅ | ✅ | |
| 본인 일정 수정/삭제 | ✅ | ✅ | |
| 타인 일정 수정/삭제 | ✅ | ❌ | 관리자: 모든 임원 |
| 공통 일정 등록/수정 | ✅ | ✅ | 2026-05-14 결정: 모든 인증 사용자 가능 |
| 공통 일정 삭제 | ✅ | ✅ (본인 등록분) | 본인이 등록한 공통 일정만. 관리자는 전체 |
| 사용자 초대 | ✅ | ❌ | |
| 사용자 역할 변경 | ✅ | ❌ | |
| 대리 입력 권한 부여 | ✅ | ❌ | |
| 대리 입력 실행 | 권한 불필요 | 권한 보유 시 | 별도 권한 필요 |
| 공휴일 관리 | ✅ | ❌ | |
| 연락처 관리 | ✅ | ❌ | |
| 엑셀 다운로드 | ✅ | ✅ | |
| 감사 로그 조회 | ✅ | ❌ | |
| 관리자 메뉴 접근 | ✅ | ❌ | |

## PERM-001: 역할 기반 접근 제어

| 항목 | 내용 |
|------|------|
| **기능 ID** | PERM-001 |
| **기능명** | 역할 기반 접근 제어 (RBAC) |
| **Phase** | 1 |
| **설명** | 사용자의 역할(관리자 / 일반)에 따라 기능 및 데이터 접근 범위가 서버 수준에서 강제된다. |

### 사전 조건

- 모든 사용자는 유효한 세션을 보유해야 한다 (AUTH-004 참조).
- 사용자 역할이 올바르게 설정되어 있어야 한다.

### 접근 제어 레이어

접근 제어는 다음 두 가지 수준에서 이중으로 적용된다.

1. **화면 접근 제어**: 모든 요청에서 세션 유효성과 역할을 검증한다. 역할에 맞지 않는 화면 접근 시 대시보드로 이동시킨다.
2. **데이터 접근 제어**: 개별 기능 수행 시 서버에서 역할과 권한을 재검증한다. 검증 실패 시 작업을 차단하고 "권한이 없습니다" 안내를 반환한다.

### 접근 제어 원칙

| 데이터 유형 | 조회 권한 | 등록/수정 권한 | 삭제 권한 |
|------------|:--------:|:-------------:|:--------:|
| 전체 일정 조회 | 모든 인증 사용자 | — | — |
| 개인 일정 등록 | — | 본인 또는 대리 입력 권한자 | 본인 또는 관리자 |
| 개인 일정 수정 | — | 본인, 대리 입력 권한자, 관리자 | 본인 또는 관리자 |
| 공통 일정 | 모든 인증 사용자 | 모든 인증 사용자 | 본인(등록자) 또는 관리자 |

### 처리 흐름

1. 사용자가 기능을 요청한다.
2. 시스템이 세션 유효성을 검증한다. 세션이 없으면 로그인 화면으로 이동시킨다.
3. 시스템이 현재 사용자의 역할을 조회한다.
4. 요청한 기능에 대한 권한을 검증한다.
   - 타인 일정 수정 요청 + 일반 역할 + 대리 권한 없음: "권한이 없습니다" 안내 후 차단
5. 권한이 확인된 경우 요청을 처리한다.

### 예외 처리

| 예외 상황 | 처리 방법 |
|----------|----------|
| 미인증 요청 | 로그인 페이지로 이동 |
| 권한 부족 | "해당 작업을 수행할 권한이 없습니다" 안내 후 차단 |
| 역할 변조 시도 | 세션 무효화, 재인증 요구 |

## 대리입력 권한 상태 정의

### 상태 목록

| 상태값 | 의미 |
|--------|------|
| `active` | 권한이 유효하며 대리 입력 가능 (`revoked_at`이 NULL인 레코드) |
| `revoked` | 관리자가 권한을 해제한 상태 (`revoked_at`에 해제 일시 기록) |

> 대리입력 권한은 레코드 물리 삭제 방식이 아닌, `revoked_at` / `revoked_by` 컬럼으로 이력을 보존한다.

### 상태 전이 규칙

| From | To | 조건 | 처리 주체 |
|------|----|------|---------|
| (없음) | `active` | 관리자가 대리 입력 권한 부여 | 관리자 |
| `active` | `revoked` | 관리자가 권한 해제 처리 | 관리자 |

### 전이 불가 규칙

- `revoked` 상태에서 `active`로 직접 전환 불가
- 권한 재부여가 필요한 경우 신규 권한 레코드를 생성해야 함 (이력 분리)

### 유효성 판별 기준

권한 조회 시 `revoked_at IS NULL`인 레코드만 유효한 권한으로 인정한다.

### 권한 이력 보존 항목

| 항목 | 설명 |
|------|------|
| 부여 일시 | 권한이 생성된 일시 |
| 부여자 | 권한을 부여한 관리자 |
| 해제 일시 | 권한이 해제된 일시 (`revoked_at`) |
| 해제자 | 권한을 해제한 관리자 (`revoked_by`) |

## PERM-002: 대리 입력 권한 부여

| 항목 | 내용 |
|------|------|
| **기능 ID** | PERM-002 |
| **기능명** | 대리 입력 권한 부여 |
| **Phase** | 2 |
| **설명** | 관리자가 "사용자 A가 임원 B의 이름으로 일정을 입력할 수 있다"는 대리 입력 권한을 설정한다. |

### 사전 조건

- 요청자가 관리자 역할이어야 한다.
- 대리 입력자(A)와 일정 주인(B) 모두 시스템에 등록된 사용자여야 한다.
- A와 B가 동일인이 아니어야 한다.

### 입력값

| 필드 | 타입 | 필수 | 유효성 규칙 |
|------|------|:---:|------------|
| 대리 입력자 | 사용자 ID | ✅ | 시스템에 등록된 사용자 |
| 대상 임원 | 사용자 ID | ✅ | 시스템에 등록된 사용자, 대리 입력자와 다른 사람 |

### 처리 흐름

1. 관리자가 권한 관리 페이지에서 전체 사용자 목록을 확인한다.
2. [대리 입력 권한 추가] 버튼을 클릭하면 권한 설정 화면이 나타난다.
3. 대리 입력자(A)와 대상 임원(B)을 선택한다.
4. 확인을 클릭하면 시스템이 관리자 권한을 검증하고 중복 여부를 확인한다.
   - 이미 동일한 조합의 권한이 존재하면 "이미 권한이 부여되어 있습니다" 안내를 표시한다.
5. 권한이 등록되고 감사 로그에 기록된다.
6. 권한 목록이 갱신되고 성공 토스트가 표시된다.

### 권한 해제 흐름

1. 관리자가 기존 대리 권한 목록에서 [해제] 버튼을 클릭한다.
2. 시스템이 해당 권한 레코드를 삭제하고 감사 로그에 기록한다.
3. 권한은 즉시 해제된다 (이후 요청부터 적용).

### 출력 / 결과

| 결과 | 처리 |
|------|------|
| 권한 부여 성공 | 목록 갱신, "A에게 B의 대리 입력 권한을 부여했습니다" 토스트 |
| 권한 해제 성공 | 목록 갱신, "대리 입력 권한이 해제되었습니다" 토스트 |

### 대리 입력 권한 데이터 모델

| 필드명 | 타입 | 필수 | 설명 |
|--------|------|:---:|------|
| 권한 ID | UUID | ✅ | 기본 키 |
| 대리 입력자 ID | UUID | ✅ | 대리 입력을 수행하는 사용자 |
| 대상 임원 ID | UUID | ✅ | 일정 주인 임원 |
| 권한 부여자 ID | UUID | ✅ | 권한을 부여한 관리자 |
| 부여 일시 | datetime | ✅ | 권한 부여 시각 |

> 동일한 (대리 입력자, 대상 임원) 쌍에 대한 중복 권한 부여는 허용되지 않는다.

### 예외 처리

| 예외 상황 | 처리 방법 |
|----------|----------|
| 권한 없는 요청자 | "관리자만 대리 입력 권한을 관리할 수 있습니다" 안내 후 차단 |
| 동일 사용자 간 대리 권한 | "본인에게는 대리 권한을 부여할 수 없습니다" 안내 |
| 중복 권한 부여 | "이미 부여된 권한입니다" 안내 |
| 존재하지 않는 사용자 | "등록되지 않은 사용자입니다" 안내 |

## PERM-003: 대리 입력 실행

| 항목 | 내용 |
|------|------|
| **기능 ID** | PERM-003 |
| **기능명** | 대리 입력 실행 |
| **Phase** | 2 |
| **설명** | 대리 입력 권한을 보유한 사용자(A)가 지정된 임원(B)의 이름으로 일정을 등록/수정한다. 이때 실제 작성자(A)와 일정 주인(B) 정보가 모두 감사 로그에 기록된다. |

### 사전 조건

- 요청자(A)가 대상 임원(B)에 대한 대리 입력 권한을 보유해야 한다.
- 요청자(A)가 유효한 세션을 보유해야 한다.

### 입력값

일정 등록 입력값에 다음 필드가 추가된다.

| 필드 | 타입 | 필수 | 유효성 규칙 |
|------|------|:---:|------------|
| 대리 입력 대상 | 사용자 ID | ✅ | 권한이 부여된 임원 |
| (기타 일정 필드) | — | — | 일반 일정 등록과 동일 |

### 처리 흐름

1. 대리 입력 권한 보유자가 일정 등록 폼을 연다.
2. 폼 상단에 "입력 대상" 드롭다운이 표시되며, 권한이 있는 임원 목록만 선택 가능하다.
3. 대상 임원(B)을 선택하면 "B 이름으로 입력 중" 경고 배너가 표시된다.
4. 일정 내용을 작성한다.
5. 저장 클릭 시 시스템이 대리 권한을 재검증한다.
   - 권한이 없거나 해제된 경우: "해당 임원에 대한 대리 입력 권한이 없습니다" 안내 후 차단
6. 일정이 저장된다.
   - 일정 주인: B (임원)
   - 실제 작성자: A (대리 입력자)
7. 감사 로그에 실제 작업자(A)와 대리 대상(B)이 함께 기록된다.
8. 일정 목록에서 "B의 일정"으로 표시되며, 일정 상세에서 실제 작성자 정보가 함께 표시된다.

### 감사 로그 데이터 모델

| 필드명 | 타입 | 필수 | 설명 |
|--------|------|:---:|------|
| 로그 ID | UUID | ✅ | 기본 키 |
| 일정 ID | UUID | ✅ | 대상 일정 |
| 작업 유형 | enum | ✅ | 등록 / 수정 / 삭제 |
| 실제 작업자 | UUID | ✅ | 대리 입력자 A |
| 대리 대상 | UUID | 선택 | 일정 주인 B. 직접 입력 시 비워둠 |
| 변경 내용 | JSON | 선택 | 변경 전/후 값 스냅샷 (수정/삭제 시) |
| 처리 일시 | datetime | ✅ | 작업 시각 |

### 일정 상세 표시 규칙

| 입력 방식 | 표시 내용 |
|-----------|----------|
| 직접 입력 | 작성자: 홍길동 |
| 대리 입력 | 일정 주인: 김임원 / 실제 작성자: 홍길동 (대리 입력) |

관리자에게는 "대리 입력" 배지가 추가로 표시된다.

### 출력 / 결과

| 결과 | 처리 |
|------|------|
| 대리 입력 성공 | 일정 생성, 감사 로그 기록, "B의 일정이 등록되었습니다" 토스트 |
| 대리 수정 성공 | 일정 업데이트, 변경 내용 포함 감사 로그 기록 |

### 예외 처리

| 예외 상황 | 처리 방법 |
|----------|----------|
| 대리 권한 없음 | "해당 임원에 대한 대리 입력 권한이 없습니다" 안내 후 차단 |
| 대리 권한 해제 후 시도 | 저장 시점에 재검증하여 동일하게 차단 |
| 대리 대상 사용자 미존재 | "등록되지 않은 사용자입니다" 안내 |
| 감사 로그 기록 실패 | 일정 저장도 함께 취소 (트랜잭션 처리), 오류 안내 표시 |
| 자기 자신을 대상으로 지정 | "본인 일정은 일반 등록 방식을 사용하세요" 안내 |

## PERM-004: 권한별 메뉴/UI 접근 제어

| 항목 | 내용 |
|------|------|
| **기능 ID** | PERM-004 |
| **기능명** | 권한별 메뉴 및 UI 접근 제어 |
| **Phase** | 1 |
| **설명** | 사용자의 역할에 따라 메뉴 항목, 버튼, 모달 등 UI 요소의 노출 및 접근을 제어한다. 화면상의 제어는 사용자 경험 목적이며, 실제 보안 차단은 서버에서 처리한다. |

### 사전 조건

- 사용자가 로그인 상태여야 한다.
- 역할 정보가 세션에서 확인된 상태여야 한다.

### UI 접근 제어 매핑

#### 사이드바 / 네비게이션 메뉴

| 메뉴 항목 | 관리자 | 일반 |
|-----------|:------:|:----:|
| 대시보드 | ✅ | ✅ |
| 일정 캘린더 | ✅ | ✅ |
| 일정 리스트 | ✅ | ✅ |
| 연락처 | ✅ | ❌ |
| 엑셀 다운로드 | ✅ | ✅ |
| 관리자 — 사용자 관리 | ✅ | ❌ |

### 처리 흐름

1. 화면 렌더링 시 서버에서 역할을 확인하여 사이드바 메뉴 항목을 조건부로 표시한다.
   - 관리자: 관리자 메뉴 섹션 포함
   - 일반 사용자: 관리자 메뉴 섹션 제외
2. 화면 주소(URL)를 직접 입력하여 접근을 시도하는 경우, 역할을 재검증하여 권한이 없으면 대시보드로 이동시킨다.
3. 일정 상세 화면에서 현재 사용자의 역할과 일정 소유권을 기준으로 버튼을 조건부로 표시한다.
   - 본인 일정 또는 관리자: [수정][삭제] 버튼 표시
   - 대리 입력 대상 일정: [수정] 버튼 표시 (삭제는 관리자만)
   - 타인 일정 (권한 없음): 버튼 미표시 (읽기 전용)

### 경로 보호 규칙

| 화면 구분 | 접근 조건 |
|-----------|----------|
| 관리자 전용 화면 | 관리자 역할만 접근 가능. 일반 사용자 접근 시 대시보드로 이동 |
| 로그인 필수 화면 | 세션 없으면 로그인 화면으로 이동 |
| 로그인 화면 | 세션이 있으면 대시보드로 이동 |

### 출력 / 결과

| 상황 | 결과 |
|------|------|
| 권한 있는 메뉴 접근 | 정상 렌더링 |
| 권한 없는 메뉴 클릭 (화면 내) | 버튼/링크 미표시 (렌더링 안 됨) |
| 권한 없는 화면 직접 접근 | 대시보드로 이동 |
